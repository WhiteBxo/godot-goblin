# 剧情编排 Markdown 写作规范（简版）

> **目的：让人方便写剧情，Codex 负责把它转换成项目现有的 JSON。** 不需要手写 JSON，不需要记运行时字段名，也不需要填写没有用到的项目。直接按自然语言写清楚剧情即可；只有涉及玩法衔接、资源绑定或关键节奏时，才需要补充对应信息。

## 一、整篇剧情开头写什么

只写与本段剧情有关的项目；不知道的不要猜，标记为「待确认」。

| 字段               | 可选项 / 写法                                                  | 限制与注意事项                                                                         |
|--------------------|----------------------------------------------------------------|----------------------------------------------------------------------------------------|
| **宿主场景**       | 实际承载剧情的场景，或「待确认」                               | 必须检查该场景真实存在；不同场景的角色、位置、音频注册不一定共用。                     |
| **启动方式**       | 进入场景自动播放 / 前一段剧情结束后播放 / 玩家与某处交互后播放 | 交互触发必须有真实交互点和宿主接线；只写前置条件不会自动开播。                         |
| **播放次数**       | 播放一次 / 可重复播放                                          | 默认播放一次；需要重播时说明重播入口及是否清理上次留下的角色、状态。                   |
| **场景与资源约定** | 主角是谁、可用角色、位置、音效、音乐                           | 只列本段会用到的。优先复用目标场景中已注册的资源，不要把 Demo 里的资源当成全项目通用。 |
| **剧情范围**       | 本段要完成什么；哪些内容不在本段处理                           | 背景设定不等于玩家台词；不要把开发备注自动写进对白。                                   |

## 二、每段剧情（Beat）写什么

每段使用一个稳定的标题，例如 `## Beat customer_arrives`。**标题必写；其余按需要填写，不适用就省略。** 标题 ID 使用简短的英文 `snake_case`，确定后尽量不要改。

| 字段                | 可选项 / 写法                                                         | 限制与注意事项                                                                                                              |
|---------------------|-----------------------------------------------------------------------|-----------------------------------------------------------------------------------------------------------------------------|
| **执行模式**        | `自动演出` / `玩家操作`                                               | 纯剧情演出可省略，Codex 默认按自动演出处理；只要涉及玩家完成任务、制作、交付、调查等玩法，就必须明确写。                    |
| **触发 / 前置条件** | 进入场景、前一段结束、某阶段、某 flag、某事件已完成、与指定交互点交互 | 只写剧情确实需要的条件。多个条件默认全部满足；不要写模糊的「条件满足后」，要说明是什么条件。                                |
| **角色**            | 谁出场、谁说话、使用哪个已存在的角色                                  | 说话人名称与游戏中的角色 ID 不是一回事。身份或角色资源未确认时写「待确认」，不要拿不匹配的占位角色冒充。                    |
| **位置 / 目标**     | 门口、柜台等已确认的位置标记；必要时写明确坐标                        | 「走到门口」只有在场景中有对应位置且可通行时才能执行。当前角色移动是直线碰撞移动，不会自动寻路；转弯要拆成多个路段。        |
| **演出顺序**        | 用自然语言按顺序写动作                                                | 「然后 / 到达后」表示先完成前一步；「同时」表示可以并行启动，但不保证同一帧精确同步。写清楚谁做什么、目标是什么、何时结束。 |
| **对白**            | 说话人 + 原文；有选择时写选项和各自后续                               | 保留用户提供的原文、标点和内心独白/实际台词区别。选项要写清楚每个选择导致什么；不要只写选项文本而不写后续。                 |
| **节奏 / 时长**     | 停顿秒数、移动速度、镜头时长、表情持续时间                            | 只对影响节奏的动作写具体数值；时间单位为秒，移动速度为世界像素/秒。未指定时 Codex 可用现有默认值并在结果中说明。            |
| **音效 / 音乐**     | 何时播放、停止、淡入淡出、是否要等音效结束                            | 使用目标场景已注册的音频。需要等有限音效播完时明确写「等待音效结束」；循环音乐不要等待它自然结束。                          |
| **结束状态**        | 设置什么阶段 / flag；下一段是什么                                     | 只写实际存在或本次明确接线的状态。成功标记应放在事件成功收尾处；不能假设失败会自动回滚已经执行的动作。                      |
| **验收结果**        | 玩家最终看到、听到、能够操作什么                                      | 用可观察结果描述，例如「顾客停在柜台，对白结束后玩家可以继续移动」，不要只写「效果正常」。                                  |

### Beat 示例

``` md
## Beat customer_arrives

- 执行模式：自动演出
- 前置条件：开场剧情已成功结束。
- 角色：顾客使用本场景已注册的 customer。
- 位置：从 door 出发，经过 aisle，最后到 counter。
- 演出：
  1. 播放门铃，等待音效结束。
  2. 主角面向右侧，镜头用 0.9 秒聚焦门口。
  3. 同时让镜头跟踪顾客，并让顾客走到 aisle。
  4. 顾客到达后继续走到 counter，面向左侧。
- 对白：顾客说：「原稿中的完整对白。」
- 验收：顾客停在柜台；演出结束后玩家恢复操作。
```

上面只是写法示例；`customer`、`door`、`aisle`、`counter` 必须在目标场景中真实可用，不能照抄到其他场景就默认有效。

## 三、只要涉及「玩家操作」，必须额外写

玩家操作 Beat 不能只写「等待玩家完成后继续」。至少说明以下信息：

| 字段                 | 必须说明什么                                            | 限制与注意事项                                                             |
|----------------------|---------------------------------------------------------|----------------------------------------------------------------------------|
| **玩家目标**         | 玩家实际要做的事情                                      | 例如查看订单、完成某张订单、制作指定配方；必须是当前项目真实支持的玩法。   |
| **完成判定**         | 什么真实结果代表成功                                    | 写明目标对象、数量、顺序等关键条件；不能用等待几秒或点击按钮代替业务成功。 |
| **前置阶段**         | 哪段剧情之后、处于什么阶段才允许开始                    | 要与前后剧情的阶段设置一致。                                               |
| **完成后续**         | 成功后设置什么状态、自动播放哪段剧情，或等待玩家触发    | 后续事件必须真实存在并接入宿主。                                           |
| **是否接受历史结果** | 可以接受进入本阶段前已完成的结果 / 必须在本阶段重新完成 | 涉及业务 flag 时必须明确；不能擅自重置订单、库存或其他业务状态。           |
| **取消 / 重试**      | 关闭界面是否保留进度、失败后怎么重试                    | 关闭未完成的弹窗不代表任务完成；失败或取消默认不会自动重播后续剧情。       |

如果当前没有真实业务信号、flag 或交互入口，写「待实现 / 待确认」。Codex 应列出缺口，不得伪造一个完成状态来让剧情看似可运行。

## 四、写作时只记住这些限制

1.  **先写清楚剧情，再让 Codex 转换。** 不要手写 JSON，也不要把 `command`、`wait` 等运行时字段当作必需的创作语法。
2.  **顺序要明确。** 「然后」是先后；「同时」是并行意图。不要要求当前系统无法表达的帧级同步。
3.  **资源不能猜。** 角色、位置、音频、场景和业务状态都要在目标场景或代码里确认；不确定就写「待确认」。
4.  **不支持的能力不能靠文案伪装。** 例如寻路、切场景、给予物品、任务系统或复杂分支，如果当前没有真实实现，应先标记缺口。
5.  **不要用等待时间代替玩法。** 玩家操作必须由真实业务结果判定。
6.  **不要擅自扩写对白或剧情。** 原稿没写的台词、音效、反应、角色行为都不要自行补充。
7.  **局部修改只改相关 Beat。** 保持其他 Beat 的内容和稳定 ID 不变；修改后重新生成受影响的 JSON 并验证。
8.  **验收要如实。** 自动校验通过不等于画面和节奏已经人工试玩通过；最终要报告未解决的「待确认」项。

## 五、推荐给 Codex 的任务指令

> 按项目现有剧情编排规范，将指定 Markdown 转换为可执行剧情。Markdown 是剧情内容的唯一来源；你负责把自然语言翻译成当前项目支持的 Story、Dialogue 和必要的 Gameplay Bridge JSON。先检查目标场景、资源注册、状态与实际业务能力；不要编造资源、扩写对白或新增未实现的运行时指令。缺失信息标记为待确认，完成后运行相关验证并报告结果。
