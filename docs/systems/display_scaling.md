# 分辨率与窗口缩放适配

## 当前策略（2026-10-24）

游戏以 640×360 为设计基准，使用 `canvas_items`，直接在窗口分辨率绘制。`DisplayScaling` 在启动及尺寸变化后计算倍率，窗口拖动按 0.12 秒合并更新；世界与 UI 使用同一个画布变换。项目默认仍为 1280×720 窗口。

优先充分利用画面空间、保留素材细节。能容纳至少 2 倍设计画布时，选用整数倍率 `k`，逻辑视野为 `window / k`。768p、900p 和 16:10 不再固定为 640×360 后留下大圈黑边，而是展示更多周围环境。原生 64px / 128px NPC 图集保持各自分辨率；不先压成小图再放大。

最大化时容忍高度相对 360 整数倍的 4% 偏差，避免 1080p 屏幕扣掉标题栏后突然从 3 倍降到 2 倍。整数除法最多留下 `k−1` 个物理像素的余量。逻辑视野上限为 1280×720，极端比例超出上限时采用 KEEP 居中，避免无限扩展。

小于 2 倍设计画布的窗口保留 640×360 设计基准，使用 fractional / expand；这是构图与可读性优先的取舍，避免旧的 1 倍 UI 过小、视野突然扩大。最小窗口为 640×360，受实际屏幕尺寸封顶。最近邻过滤保留边缘，但非整数倍率下像素宽度会有差异。

## 典型尺寸

| 窗口 | 逻辑基准 | 倍率 | 结果 |
| --- | --- | --- | --- |
| 1024×600 | 640×360（expand） | 约 1.6 | 保住小窗口的构图和 UI 可读性 |
| 1280×720 | 640×360 | 2 | 原有设计构图 |
| 1366×768 | 683×384 | 2 | 铺满，略扩展周围环境 |
| 1600×900 | 800×450 | 2 | 铺满，扩展视野 |
| 1920×1061 | 640×353 | 3 | 最大化窗口保持 3 倍 |
| 1920×1080 | 640×360 | 3 | 原有设计构图 |
| 1920×1200 | 640×400 | 3 | 向上下扩展 |
| 2400×1080 | 800×360 | 3 | 超宽屏向两侧扩展 |
| 2560×1440 | 640×360 | 4 | 原有设计构图 |
| 3840×2160 | 640×360 | 6 | 原有设计构图 |

这里的整数倍率描述逻辑画布到窗口；角色场景自身的缩放、地图密度和 Camera2D.zoom 仍会共同决定每个素材像素的最终屏幕大小。聚落保持原有 1 倍跟随镜头；奶茶店按完整房间边界计算镜头，因此在较大的逻辑视野中整间店仍充满画面。

`BoundedFollowCamera._screen_factor()` 同时核对窗口宽高与实际逻辑视口，整数分支取实际整数倍率。小窗口 fractional 分支保留原定镜头缩放，不再为了取整意外退远。镜头移动、边界、演出接口和物理单位不变。

## 验证

- `tests/verify_display_scaling.gd`：典型尺寸、标题栏容差、超宽上限、计划应用及小窗口退路。
- `tests/verify_visual_resolutions.gd`：真实渲染上下文下，1024×600、1280×720、1366×768、1600×900、1920×1080、2400×1080 的奶茶店／聚落画面、HUD 按钮边界、玩家可见性和小窗口对话。加 `-- --capture` 保存到 `.godot/visual_resolution_check/`。
- `tests/verify_touch_controls.gd`、`verify_camera_director.gd`、`verify_shop_camera.gd`：直接消费者的布局和镜头边界。

本次实际结果与角色素材修正见 [清晰度验收](../assets/imports/pixel_npc_clarity_2026_10_24.md)。4K 只验证布局计划，未在真实 4K 显示器上试玩；手机只验证横屏尺寸和触摸布局，未做真机验收。

依据 [Godot 4.7 多分辨率](https://docs.godotengine.org/en/4.7/tutorials/rendering/multiple_resolutions.html) 和 [Window](https://docs.godotengine.org/en/4.7/classes/class_window.html)：canvas_items 在目标分辨率绘制；content_scale_size、aspect 与 stretch 共同决定逻辑视口和缩放。
