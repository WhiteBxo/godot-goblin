# 分辨率与窗口缩放适配

## 问题

游戏按 640×360 设计，`stretch/mode = canvas_items`、`stretch/aspect = expand`。
当 `stretch/scale_mode = integer` 时，引擎会把缩放倍数向下取整，**但取整后不会
把扩展过的逻辑视口补回去**，于是只有「窗口尺寸恰好等于基准 × 整数」时才铺满：

| 窗口 | 取整后的缩放 | 实际覆盖 | 结果 |
| --- | --- | --- | --- |
| 1920×1080 | 3.0 | 1920×1080 | 铺满 |
| 1600×900 | 2.0 | 1280×720 | 四周各 160×90 黑边 |
| 1366×768 | 2.0 | 1280×720 | 右下缺 86×48 |
| 1280×600 | 1.0 | 768×360 | 只占屏幕 60% |

主流手机横屏是 1080 高，正好是 360 的 3 倍，所以这个问题在手机上长期没被看见；
桌面窗口化、平板、折叠屏、分屏以及导航栏没吃干净的全屏都会露出来。

## 规则

`DisplayScaling`（autoload，`src/core/display/display_scaling.gd`）在启动和窗口
尺寸变化后，把**逻辑基准分辨率改成「窗口尺寸 ÷ 能放大的整数倍」**：

```
k = floor(min(宽 / 640, 高 / 360))
base = (宽 / k, 高 / k)          # k >= 2 时
```

此时 `scale` 正好等于 `k`，画面铺满，每个逻辑像素都是整齐的 k×k。

两条兜底：

- `k < 2`（窗口比 640×360 大不了多少）→ 退回 `fractional`。整数缩放本来就没得选，
  这时铺满优先，代价是像素取样不均。
- `base` 面积超过设计分辨率的 1.6 倍 → 退回 `fractional`。窗口比例离谱时
  （导航栏占位后的 2400×1016、折叠屏内屏等）硬撑整数倍会把视野放到设计之外，
  不如保住原本的构图。

## 各设备结果

| 设备 / 窗口 | k | 基准 | 相对 640×360 |
| --- | --- | --- | --- |
| 1080p 手机（2400×1080） | 3 | 800×360 | 与 expand 原本行为一致，无变化 |
| 2K 手机（3168×1440） | 4 | 792×360 | 同上 |
| 1366×768 笔记本 | 2 | 683×384 | 视野 +14% |
| 1600×900 窗口 | 2 | 800×450 | 视野 +56% |
| 1280×600 小窗 | 1 | 640×360（fractional） | 构图不变，像素取样不均 |

像素精灵的**物理尺寸始终是 k 倍**，动态基准不会把角色缩小；变化的是能看到的
世界范围，以及按视口比例排版的 UI（立绘、对话框高度）会跟着基准微调。

## 为什么不直接全局改 fractional

640×360 + nearest 过滤 + 像素字体，在 2.5 倍这类比例下笔画会出现 2px/3px 混排，
移动时像素边界逐帧跳动。实测对比见 `.workbuddy/memory/2026-10-20.md` 的记录，
标题文字放大 4 倍后差异明显。整数基准能同时拿到铺满和像素齐整。

## 触摸层

`src/UI/touch/touch_controls.gd` 的布局以 640×360 写成常量：贴边的键走 `_place()`，
顶部暂停键走 `_place_centered()` 保持「视口中心 + 32px」。`expand` 或动态基准都会
让逻辑视口变宽，居中键不能按「超过参考宽一半就贴右」处理，否则会被推到右侧。

## 验证

- `tests/verify_display_scaling.gd`：各档位基准与覆盖不变式（`base × scale` 等于窗口，最多差 1px）。
- `tests/verify_touch_controls.gd`：超宽视口下暂停键居中、摇杆与动作键贴边。
- 实拍验收：分别在 1600×900、1366×768、2400×1080、1280×600 下确认 `gap = 0`。
