# 测试与分级验证

本文件规定整个项目如何选择、执行和报告验证；修改测试及其他目录中需要验证的代码、场景或数据时均适用。

## 先说明风险，再选择级别

开始验证前用一两句写明“本次改动的风险点 → 要执行的检查”。默认选择最低必要级别，有明确升级依据才扩大范围；对白、立绘、音效引用、单个 Beat 参数和纯文档不得默认运行完整项目回归。

| 级别 | 触发条件 | 执行范围 |
| --- | --- | --- |
| 局部验证 | 单个 Beat 参数、逐字对白、立绘或音效引用、单场景内节点 / 数值调整 | 对应对象的清单校验、资源解析、宿主 F6 观察；未迁移剧情用 `tools/story/validate_story.gd`，结构化工程用 `tools/story/edit_story_project.gd`，需要执行时用独立预览入口选择受影响事件，见[编排指南](../docs/guides/story_editor.md) |
| 模块验证 | 模块内部逻辑，或影响其多个场景 / 调用方，例如步骤类型、对白解析、UI 弹窗、Bridge phase | 模块测试脚本，加直接调用方的最小验证；按模块 `AGENTS.md` 选择候选 |
| 完整回归 | 核心公共接口、跨模块状态契约、场景生命周期、共享数据格式变更、大规模重构、发布验收 | `python tests/run_all.py` 跑 `tests/` 下全部 `verify_*.gd`，需要 Python 校验时加 `--include-python`；结果按基线对照记录 |

纯文档仅检查内容、Markdown 链接、格式与 Git diff，不运行引擎或项目测试。用户明确指定完整回归、发布验收或测试范围时，以用户要求为准。

## 全量回归：统一运行器

完整回归只走一个入口：`python tests/run_all.py`。每项测试在独立 Godot 进程中运行，超时由运行器强杀进程树，协程中断或漏掉 `quit()` 都不会让 CI 无限等待。

| 退出码 | 结论 | 含义 |
| --- | --- | --- |
| 0 | PASS | 脚本正常结束且未记录失败 |
| 1 | FAIL | 断言失败，或退出码为 0 但日志里出现脚本错误 |
| 2 | SKIP | 需要外部夹具（`--fixtures=` / `--from-save=`）、缺可选依赖，或当前环境不具备该测试的前提 |
| 124 | HANG | 超时被强杀（日志里若已有脚本错误，报告会一并给出该行） |

运行器自身退出码：出现 HANG 返回 124，否则有 FAIL / CRASH 返回 1，全部通过返回 0。

- 参数：`--jobs`（默认 4）、`--timeout`（全局覆盖单项预算）、`--filter`、`-v`、`--list`、`--include-python`、`--godot`、`--strict-known`，默认值见 `--help`。
- 单项差异登记在 `tests/run_all.py` 的 `PROFILES`，不要散落到测试脚本里：需要真实渲染上下文（读回像素）的去掉 `--headless`；需要编辑器实例的记 SKIP 原因；等待剧情事件、天然较慢的给单独预算。
- 结果写到 `.godot/test_logs/`（不提交）：每项一份 `<name>.log`，汇总 `run_all.json`；目录在每次运行前清空。

### 已知红台账

`tests/known_red.json` 登记「已接受但尚未修复」的失败项，命中项在报告里记为 `KNOWN`，不影响退出码，但会连同原因一起打印。用途只有一个：把少数**无法在当前环境稳定复现或已明确属于测试代码自身缺陷**的失败从「每次都红、于是没人再看」里摘出来，而不是给产品缺陷开后门。

- 每条必须有 `category`（`product-bug` / `test-drift` / `environment`）与 `reason`，写得让下一个人能直接判断该不该修。
- `product-bug` 只能短期停留：要么修掉，要么把设计取舍写清楚并改写测试期望，不能长期挂在台账里。
- 台账里的项一旦恢复通过，运行器会提示「台账过期」，此时删除该条；台账腐烂比没有台账更糟。
- 发布验收用 `python tests/run_all.py --strict-known`，已知红也按失败计。
- 推送前钩子由 `python tools/git/install_hooks.py` 安装，跑完整回归后才允许 push；临时跳过用 `SKIP_REGRESSION=1 git push`。

写测试时要让失败可见，不要把断言失败伪装成挂起：

- 主流程无论成败都必须走到 `quit(0 / 1)`；只 `free()` 到函数末尾、依赖引擎自行退出会一直挂住。
- 前置条件失败（场景装配不出预期类型、数据加载返回错误、节点路径改型）先 `check` 再立即 `quit(1)` 返回，不要继续访问已在报错对象的下游字段——GDScript 没有异常，脚本报错会直接中断协程。
- 需要外部夹具时 `quit(2)` 并打印所需参数，让运行器把它记成 SKIP 而不是失败。

## 执行边界

- 模块规范和文档列出的脚本、命令、F6 场景都是候选项，不是每次必跑清单；选择与本次风险直接对应的检查，汇报未执行其余项的原因。
- 同一任务内相关代码、配置和测试数据未变化时，同一测试只执行一次；通过后不为再次确认而重跑。
- 失败先归因。只有能对应本次 diff 的失败才在本任务调查修复；疑似历史失败、环境 / 渲染器诊断或无关模块失败，先以未改动状态或既有基线判断，确认无关后记录并继续。
- 修复后只重跑受影响的测试；修改触及其他模块时才升级范围，不为处理历史失败扩大任务。
- 新测试只验证实际行为与重要边界，不为低影响修改编写重复实现的测试。测试文件按 `verify_<module>.gd` 等现有分类放置，数据放 `fixtures/`。
- 修改夹具前确认使用它的直接测试，不把无关快照或大段临时日志提交进仓库。Godot 测试脚本的 UID、资源路径同样遵守通用文件规则。
- 报告实际执行的命令 / 检查、结果、未执行项、基线与无关历史失败；需要画面或交互验收时给出 F6 入口和可观察结果，不以静态检查替代试玩结论。
