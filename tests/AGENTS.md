# 测试与分级验证

本文件规定整个项目如何选择、执行和报告验证；修改测试及其他目录中需要验证的代码、场景或数据时均适用。

## 先说明风险，再选择级别

开始验证前用一两句写明“本次改动的风险点 → 要执行的检查”。默认选择最低必要级别，有明确升级依据才扩大范围；对白、立绘、音效引用、单个 Beat 参数和纯文档不得默认运行完整项目回归。

| 级别 | 触发条件 | 执行范围 |
| --- | --- | --- |
| 局部验证 | 单个 Beat 参数、逐字对白、立绘或音效引用、单场景内节点 / 数值调整 | 对应对象的清单校验、资源解析、宿主 F6 观察；未迁移剧情用 `tools/story/validate_story.gd`，结构化工程用 `tools/story/edit_story_project.gd`，需要执行时用独立预览入口选择受影响事件，见[编排指南](../docs/guides/story_editor.md) |
| 模块验证 | 模块内部逻辑，或影响其多个场景 / 调用方，例如步骤类型、对白解析、UI 弹窗、Bridge phase | 模块测试脚本，加直接调用方的最小验证；按模块 `AGENTS.md` 选择候选 |
| 完整回归 | 核心公共接口、跨模块状态契约、场景生命周期、共享数据格式变更、大规模重构、发布验收 | `tests/` 下全部相关 `verify_*.gd` 及 `tests/verify_story_authoring.py`，结果按基线对照记录 |

纯文档仅检查内容、Markdown 链接、格式与 Git diff，不运行引擎或项目测试。用户明确指定完整回归、发布验收或测试范围时，以用户要求为准。

## 执行边界

- 模块规范和文档列出的脚本、命令、F6 场景都是候选项，不是每次必跑清单；选择与本次风险直接对应的检查，汇报未执行其余项的原因。
- 同一任务内相关代码、配置和测试数据未变化时，同一测试只执行一次；通过后不为再次确认而重跑。
- 失败先归因。只有能对应本次 diff 的失败才在本任务调查修复；疑似历史失败、环境 / 渲染器诊断或无关模块失败，先以未改动状态或既有基线判断，确认无关后记录并继续。
- 修复后只重跑受影响的测试；修改触及其他模块时才升级范围，不为处理历史失败扩大任务。
- 新测试只验证实际行为与重要边界，不为低影响修改编写重复实现的测试。测试文件按 `verify_<module>.gd` 等现有分类放置，数据放 `fixtures/`。
- 修改夹具前确认使用它的直接测试，不把无关快照或大段临时日志提交进仓库。Godot 测试脚本的 UID、资源路径同样遵守通用文件规则。
- 报告实际执行的命令 / 检查、结果、未执行项、基线与无关历史失败；需要画面或交互验收时给出 F6 入口和可观察结果，不以静态检查替代试玩结论。
